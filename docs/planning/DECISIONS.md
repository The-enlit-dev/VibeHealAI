**Precedence:** where any other document in this repository conflicts with this log, this log wins. Other planning documents explain *how* these decisions are carried out.

**Labels used across the planning set**

| Label | Meaning |
|---|---|
| **[Decision]** | Explicitly decided by the project owner. Recorded here. |
| **[Verified]** | Checked against inspected code, repository content or official documentation on the date given. Re-check before relying on time-sensitive facts. |
| **[Recommendation]** | A professional proposal. Not decided until the owner approves it. |
| **[Assumption]** | Believed but not verified. Must be checked. |

## 4. Round 3: backend-managed integration marketplace (recorded 2026-10-31)

### Why the direction changed
The owner approved a backend-managed, extensible integration marketplace with nine priority providers (DEC-17 to DEC-19). Provider integrations need OAuth client secrets, app private keys and access tokens. Those must **not** live in a desktop app, where any user can extract them. A backend is therefore needed to hold credentials and call provider APIs for the desktop app (DEC-18, DEC-20).

### What it replaces
| Earlier plan (v3, 2026-10-29) | Status now | Reason |
|---|---|---|
| "No accounts, cloud services or network connections in the MVP" (CLAUDE.md, README, NP-1) | **Superseded** for integration features. The core safety workflow still works offline and sends nothing anywhere | Integrations need network access to providers. They are opt-in and connect only after the user acts |
| "The app opens no network ports" (WN-2) | **Superseded in part.** The local backend listens on the loopback interface only (BK-1). The desktop window still talks only to its own main process | A separate backend process needs a local HTTP interface |
| "VibeHeal stores no credentials" (SE-4) | **Superseded** by CR-1 to CR-6 | Provider tokens must be stored somewhere. The backend encrypts them |
| "No GitHub integration" (DEC-02) | **Superseded** by DEC-19 | GitHub is priority 1 |
| Netlify and Supabase "not in the MVP" (TECH_STACK §2) | **Clarified.** They are now *providers the user can connect*. VibeHeal still does **not** use Netlify to host itself or Supabase as its own database | Different roles. Hosting and databases for VibeHeal itself are still excluded (DEC-22) |
| "No plug-in abstraction is needed now" (ARCHITECTURE §8) | **Superseded** | The marketplace needs a provider registry and a common adapter interface (DEC-17) |

### What stays the same
- The core broken-project workflow and its security requirements (PB, FC, CE, SN, SE-1/2, HB, LD, WN-1/3) stay (DEC-16).
- No built-in AI or AI billing (DEC-06, DEC-24). $0 budget (DEC-05, DEC-22). Minimal, functional UI (DEC-10). npm (DEC-14). Private repository (DEC-12). Apache-2.0 intent with no LICENSE file yet (DEC-15).

### Consequences
- Security gains new requirement families: BK (backend), CR (credentials), IN (integrations and authorization) and AU (audit), in [SECURITY.md](./SECURITY.md).
- The roadmap gains an integration track (IM1 to IM4) beside the core track (M1 to M6), in [ROADMAP.md](./ROADMAP.md).
- Live provider testing needs external configuration that only the owner can do, such as registering a GitHub App (P-11). Until then, providers show **Not configured** or **Coming soon**, never fake success.
